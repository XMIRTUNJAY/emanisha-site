The content pipeline: how Priya's curriculum gets built

Why Priya never sees raw content

The tables from Part 3 are empty without trustworthy rows — this is the hub’s third chain up close. Her Liquid Clustering lesson didn’t fall from the sky — it traveled: syllabus PDF → extracted sections → generated draft → seven validators → versioned publish → search indexes → embeddings. A single script doing all of that is untestable and undebuggable at 3 AM. First principle: a pipeline is an assembly line where every station can reject the part. Follow one concept through all seven stations:

Stage What happens to Priya’s lesson
Ingest Syllabus PDF/HTML fetched, hashed (SHA-256 receipt of what arrived)
Extract Sections and objectives parsed; concept boundaries get slug IDs
Generate Draft written: 6 explanation levels, examples, practice questions, traps, resources — deterministic IDs
Validate 7 ordered checks; failures stop the lesson here, never reach her
Publish Hash-compared upsert, version bump, history snapshot
Index Full-text search updated so she can find it
Vectorize 1024-dim embedding so “like this” works

You are here: Part 4 of 6 — the factory. Parts 1–3 mapped the repo, the math, and the API; this part fills the tables they read. Part 5 wires up search and agents, and Part 6 runs the whole thing live.

Idempotency is a property of the record of the work, not the work. Your turn: add receipt-check-skip to any retryable job you own. Failed jobs land in a dead-letter queue as inspectable rows — retries become deliberate actions, and the orchestrator always knows where a run stands.

A crash, walked through

Tuesday 3 AM: the run dies during Validate (stage 4 of 7). Here is the morning:

  1. The orchestrator reads receipts: ingest, extract, generate present; validate missing.
  2. Re-run starts at Validate — the first three stages’ receipts say “done”, so they are skipped, not repeated.
  3. Validate passes on the fixed input; publish, index, vectorize proceed.
  4. Priya wakes to a normal dashboard. She never knew.

Without receipts, the only safe move is re-running everything — re-fetched sources, regenerated drafts, duplicated versions. The receipt turns “oh no, rerun” into “resume”. Note the 24-hour window: a crash discovered Friday from a Tuesday run replays from scratch. That boundary is documented, not discovered.

Validators, cheap first

Schema shape (22 fields, slug patterns, correct_answer ^[A-D]$) → syllabus boundary → terminology → accuracy → duplicates (0.85) → quality thresholds → code execution (ast.parse). Fail fast on structure before spending on substance — compilers taught us; pipelines keep forgetting. When this ordering is wrong: expensive checks burn budget rejecting what a regex caught free.

The general rule travels: order every gate sequence by cost-per-rejection, cheapest first. Model-judged accuracy goes last not because it matters least but because it costs most. And gates grow from observed failures — these seven exist because real bad content met each one, in that order of discovery.

Publishing itself is careful: hash-compared upserts (unchanged content isn’t rewritten), version bumps (history preserved), snapshots (rollback possible). Publishing is a promise to learners; these mechanics keep it.

Directing an AI agent at this pipeline

Failure modes of pipelines

  • No receipts. Every retry duplicates. Defense: receipt-check-skip per stage (verified in orchestrator.py).
  • Gates in wrong order. Expensive judges reject what regexes catch free. Defense: cost-ordered validators; re-order when you add one.
  • Silent drops. Failed items vanish; nobody knows the curriculum has holes. Defense: dead-letter queue as inspectable rows.
  • Unversioned publishes. A bad publish overwrites good content with no way back. Defense: hash-compare, version bump, snapshot — rollback is a feature.
  • Expired windows. Crash found after receipts expired replays everything. Defense: documented 24h window + alerts long before it matters (recommended, not yet built — an honest gap).

Exercises

  1. Kill a run mid-stage locally. Resume it. Which stages re-ran? (Expect: none finished twice.)
  2. Reorder two validators (cheap last). Estimate the wasted compute on a 100-lesson batch. Put the order back.
  3. Write one reversal entry for your stack in the trade-off matrix shape. If you can’t, your matrices are marketing.
  4. Inspect one dead-letter row end to end: what failed, which gate caught it, what a human does next.
  5. Ask an AI agent to add a validator with the Topic 7 prompt. Check: receipt scheme reused? Position justified by cost?

Five things to take with you

  1. Every station can reject the part — that is what makes it a pipeline, not a script.
  2. Idempotency lives in the record of work, not the work.
  3. Order gates cheapest-first; let observed failures grow the list.
  4. Models draft, gates decide — policy in five words.
  5. Publish carefully: compare, version, snapshot — rollback is a feature.

What worked, what I’d change

Worked: stage independence (each runnable alone against yesterday’s output), receipts, ordered gates. Changed already: validators grew from schema-only to seven as real failure classes appeared — gates follow observed failures, never imagined ones. Principle: let production teach you what to validate; write it down so it teaches once.
