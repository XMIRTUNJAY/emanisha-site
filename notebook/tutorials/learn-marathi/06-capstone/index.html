Full-flow recap

One direction, no hand edits. The Flutter app’s 26 unit files and 1,002-word vocabulary feed npm run sync, which validates every key and row, applies the logged override file, and writes three committed snapshots with counts stamped in meta.json. Page datasets in src/data/seo/*.json reference those snapshots through data hooks; src/lib/seo.ts resolvers turn hooks into rows and throw on anything unresolvable. tools/validate-content.mjs gates the build on schema, uniqueness, thresholds, links, and script hygiene. Astro renders 200 static pages with per-page SEO heads, related-links blocks, and exactly one contextual CTA panel each — all funneled through one config file toward a waitlist, because the app isn’t launched yet. A Hindi mirror reuses the same data with translated chrome and reciprocal hreflang. That is the whole machine.

Stealable principles

  1. Count before you create the page. Entries per cluster, resolved rows per dataset page, lessons per unit — numbers decide URLs.
  2. Make bad content unrenderable. Resolvers throw, validators block, drafts stay drafts until they clear the bar.
  3. One direction, no hand edits. Canonical data flows through scripts into snapshots; corrections land in a logged override layer, never in the output.
  4. One CTA panel per page. Count panels like pages; a second one is lying about being necessary.
  5. Gate every promise in config. If the thing doesn’t exist yet, the site must be physically incapable of offering it.
  6. Mirror chrome, never data. A second language is a dictionary over the same snapshots, not a second copy.
  7. Scale the checks with the pages. Every growth mechanism ships with its audit: manifests, reports, checker scripts, counts.

Rebuild one slice yourself

Pick a real topic with 15 or more words in the snapshot — Animals (40), Clothing (38), or Emotions (20). Then:

  1. Write one dataset entry (vocabulary family): slug, title under 60 characters, description 60–155 characters, one search intent, topics, and data hooks pointing at the real category.
  2. Add three practice items and two wrong-vs-right mistakes with the why.
  3. Run npm run content:qa — fix every failure it reports (thresholds, lengths, links).
  4. Run npm run build — confirm your page renders and appears in the manifest and sitemap.

Done means: QA passes, the build passes, the page shows only resolved rows, its related block has no dead ends, and exactly one CTA panel points at the funnel. You just did, at small scale, everything Parts 1–5 describe. The only difference between your slice and the 200-page site is repetition — and repetition with gates is the entire game.
