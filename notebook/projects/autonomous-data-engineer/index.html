Autonomous Data Engineer

Give it an objective in plain words; it plans, calls tools, waits for your approval where it matters, and leaves a trace you can replay — and the record of how it was reasoned into existence.

Two ways to read this page

  • Understand the system: The spark → The struggle → The decisions → How it works → Where it stands → Reflection.

“An agent that cannot show its work is a rumor with an API key.”

The project began the day a data job failed silently for the third time and nobody could say what it had done, in what order, or why. Not a bigger model — a stricter machine: every run is a task, every task is steps, every step is recorded, and the dangerous steps wait for a human. If you take one thing from this page, take the order — accountability first, autonomy second.

The spark

Data work fails in ways chatbots never see: a scraper that returns yesterday’s table with today’s date, a transform that silently drops rows, a 3 AM pipeline nobody watches. Each failure here is investigated the same way — what ran, what did it touch, what did it decide — and the tooling kept being rebuilt per incident. So the tooling became the project: one registry of typed tools, one state machine that runs them, one approval table that can stop them, one trace log that remembers them.

The proving ground is real Indian government scheme data — data/sample_schemes.csv is 21 rows by 7 columns of the exact shape the scrapers chase (data.gov.in, PIB releases, budget documents, scheme portals, news). Synthetic rows would have made every demo pass and taught nothing; the sample is small enough to read and real enough to embarrass.

The struggle

Three things went wrong enough to leave marks. All three are still visible in the repo, which is the point.

The tools had no contracts. Early tools were bare functions — a scraper returning whatever shape it felt like, a profiler with no declared inputs. The fix was the registry: every tool is a ToolDefinition with typed inputs, and verify_ade.py asserts the exact set — nine names, from list_files to scrape_news. Add a tenth and the verifier fails until the contract exists. That friction is the feature.

The agent had no memory of itself. The first orchestrator ran plans and forgot them — a retry repeated the mistake identically, and there was no way to ask what happened. The fix is the trace layer: OpenTelemetry spans plus a traces/{run_id} endpoint and an agent/runs/{run_id}/replay endpoint. A run can be re-walked step by step after the fact. Debugging stopped being archaeology.

Approval was a comment, not a constraint. “Ask the user before destructive steps” lived in a docstring that nothing enforced. The fix is schema: TaskStatus.WAITING_APPROVAL, an ApprovalStatus enum, and an approval_requests table with types, statuses, and approver records. Awaiting tasks are queryable rows, not polite intentions.

And one honest admission: the repo carries debug_test.py through debug_test3.py plus a stray ?TEMPhermes-verify-ade.py at the root — the fossil record of late-night debugging that never got swept. The verification scripts (verify_ade.py, verify_full.py) are the grown-up versions of the same instinct: don’t trust it, check it.

The decisions

State machine, not a chat loop

Problem
Long data jobs need resumability, inspection, and stopping points — a conversation transcript provides none of these.
Options considered
  • ReAct-style chat loop
  • Explicit task/step state machine
  • DAG workflow engine (Airflow-style)
Chosen
Task and TaskStep rows with status enums (IDLE, WAITING_APPROVAL, ...), driven by AgentOrchestrator in packages/agent/orchestrator.py.
Why
Every run is queryable mid-flight; a failed step retries without replaying the world; approval is a state, not a hope.
Trade-offs
More machinery than a loop: states, transitions, and persistence for every hop. Cyclic or branching plans need the planner to stay simple — the machine executes, it does not improvise control flow.
Result
Tasks, steps, approvals, and traces all live in Postgres; the Next.js dashboard reads the same rows the agent writes.

Approval as database rows

Problem
Destructive or expensive steps must wait for a human — and 'wait' must survive restarts, reloads, and forgetfulness.
Options considered
  • Docstring conventions
  • In-memory pause flags
  • approval_requests table + WAITING_APPROVAL state
Chosen
ApprovalRequest rows (type, status, approver, timestamps) and tasks parked in WAITING_APPROVAL until resolved.
Why
A paused run is visible in the dashboard, resumable after a restart, and auditable afterward — the three things flags and comments cannot give.
Trade-offs
Every gated step pays a round trip through the human. Set the gate too wide and the 'autonomous' engineer becomes a notification engine that needs babysitting.
Result
The schema enforces what the docstring only suggested; nothing destructive runs unapproved.

Polars and DuckDB first, PySpark behind glass

Problem
Govt data tasks range from 21-row samples to lake-scale dumps — one engine either wastes clusters or chokes locally.
Options considered
  • PySpark for everything
  • Pandas everywhere
  • Polars/DuckDB default, PySpark sandboxed for scale
Chosen
Polars 1.16 + DuckDB 1.1 for the default path; PySpark 3.5 + Delta for heavy jobs with sandboxed execution (test_pyspark.py probes the boundary).
Why
Small data stays instant and dependency-light; big data still has an escape hatch that cannot touch the host carelessly.
Trade-offs
Three compute idioms to maintain (eager frames, SQL, Spark). The sandbox boundary is probed by tests, not proven by audit — treat it as a fence, not a vault.
Result
The 21×7 sample profiles in milliseconds; the architecture doesn't fall over when the sample grows up.
Decision Option A Option B Chosen Why
Control Chat loop State machine State machine Resumable + inspectable
Approval Convention Schema rows Schema rows Survives restarts
Compute One engine Tiered (Polars/DuckDB → Spark) Tiered Fast default, safe scale

Neither table is universal advice. Each row holds only under this project’s constraints: one operator, real but small data, danger in the toolset. Change the constraints and the answers change — that is what makes them decisions rather than preferences.

How it works

  • Python 3.11
  • FastAPI
  • PostgreSQL + pgvector
  • Polars
  • DuckDB
  • PySpark (sandboxed)
  • APScheduler
  • Great Expectations
  • Next.js 13

The whole system is one loop — objective, plan, approve, execute, trace, replay — drawn below as the machine sees it. Six terms, explained once and never again:

  • API. A menu of URLs. POST /tasks starts work, POST /tasks/{id}/run runs it, GET /tasks/{id} asks how it’s going.
  • Orchestrator. The state machine in packages/agent/orchestrator.py: idle → planning → waiting_approval → executing → done, with every transition recorded.
  • Tool registry. Nine typed tools (list_files, inspect_file, profile_dataset, plus six gov-data scrapers). The LLM plans; only registered tools act.
  • Approval gate. Steps the planner flags land in approval_requests; the task parks in WAITING_APPROVAL until a human resolves them.
  • Trace layer. OpenTelemetry spans plus run records — GET /traces/{run_id} reads them, POST /agent/runs/{run_id}/replay re-walks them.
  • Dashboard. A single-page Next.js app (zustand + chart.js) reading the same Postgres rows — tasks, approvals, traces.

Three chains connect requirements to what got built:

Jobs must be resumable → memory lives in rows, not RAM → task/step/approval/trace tables. Kill the process mid-run and the dashboard still shows exactly where it stopped.

Tools must be trustworthy → nine typed definitions, asserted by name. The verifier fails on the tenth tool until its contract exists — the registry grows deliberately or not at all.

Scale must not endanger the host → tiered compute. Polars and DuckDB do the daily work; PySpark sits behind the sandbox probe for the day the data outgrows the laptop.

Why the model plans but never touches data

The LLM writes plans from the nine registered tools and never executes anything itself. Every side effect passes through a typed tool, a recorded step, and — where flagged — a human. Capability without contact.

Follow one run end to end (module names real): the API creates the task row, the orchestrator plans with planner/llm_planner, gated steps land in approval_requests, tools execute through tools/registry, spans flow to the observability collector, and the dashboard polls the same rows. Handlers stay thin; the machine lives where the schema can see it.

Who remembers what: Postgres holds everything that matters (tasks, approvals, traces — back it up). The .env points at Postgres on port 5434, database ade. The browser holds nothing important, which is why closing the dashboard mid-run costs nothing submitted.

Running it costs the machine plus Postgres — containers or local services, no per-run model bill for the machine itself (the planner calls are the only model spend, per plan not per step). That shape is designed, not lucky: the expensive brain works once per plan, the cheap machine works every step.

How AI was actually used here

The planner is an LLM and the loop around it is not: plans are proposed in words, executed as typed tool calls, gated by schema, judged by traces. What gets delegated: decomposition, tool choice, parameter filling. What doesn’t: permission (human rows), memory (database rows), truth (typed results).

Verification is mechanical, not hopeful: verify_ade.py for the loop, verify_full.py for the 26 checks, pytest unit/integration/evaluation suites underneath. New tools need contracts before they need implementations.

One gap I’ll name plainly: the /tools/{name}/execute endpoint lets any caller run any tool with no approval path — the gate covers planned runs, not direct execution. Direct calls are the operator’s own hands, but the asymmetry is real: the front door has a guard, the side door has a sign.

Reflection

What worked. Schema-first approval — parking in rows instead of pausing in RAM is the decision I’d defend anywhere. Typed tools with a named verifier. Traces plus replay turning debugging from archaeology into re-walking.

What didn’t. Debug fossils at the root (sweep them). The side-door execute endpoint with no gate (flagged above). Sample-scale confidence standing in for production evidence.

What surprised me. How small the honest core is: nine tools, one state machine, one gate, one trace log. Everything else is honest plumbing around it.

What I’d change. Gate direct tool execution the same as planned steps. Write the dimension contract for embeddings before the first vector lands (pgvector is imported; the discipline isn’t demonstrated yet). Sweep the debug files.

What remains unsolved. Whether approval scales — one operator approving occasional gates is pleasant; continuous operation is a queue with a human as the bottleneck. That experiment is scoped and waiting: measure reviewer load, then decide if gates need tiers.

Build your own

Reproduce it exactly (install, .env with the Postgres URL, verify_ade.py — nine tools green is your checkpoint), then: add a tenth tool and watch the verifier demand its contract; park a task in WAITING_APPROVAL, restart everything, and confirm it waited; replay a run from its trace and find the step you’d have stopped; point a scraper at a live portal and see which assumption breaks first — write that one down, it becomes the project’s next decision.

Five things worth keeping: permission lives in rows, not comments. Nine typed tools beat ninety hopeful functions. Trace everything; replay beats recollection. The model plans, the machine permits. Small real data beats big synthetic data.
