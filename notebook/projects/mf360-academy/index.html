“If every LLM provider goes offline, the website keeps working — only the future content pipeline pauses.”

That sentence from the README is the whole project. Most “AI learning platforms” are thin wrappers around an API call that bills per student per click. This one inverts it: the AI works the night shift in an offline pipeline, and the website serves finished intelligence from a store. Students get instant answers with zero latency, zero per-request cost, and zero hallucination risk at serving time — because nothing is generated at serving time.

The spark

Certification prep has two failure modes, and they look like opposites. Static question banks rot: syllabi change, questions leak, answers go stale, and nobody knows which items still hold. AI tutors, meanwhile, invent confidently: plausible explanations for wrong answers, outdated syllabus coverage, confident nonsense at $0.03 a question. One rots, the other hallucinates.

So the academy splits the problem across time: an offline pipeline where AI is allowed to draft, argue, and be wrong — with validators, versioning, and publishing gates before anything reaches a student — and a runtime that serves only what survived. Generation is optimistic; serving is deterministic. The content store sits between them as the membrane.

The first syllabus is Databricks Certified Data Engineer Professional — chosen because the sibling Mastery platform already mapped that territory, and because data engineers pay for credentials that employers verify.

The struggle

Two things went wrong enough to leave marks, and one honest empty room.

The engine came before the content. The deterministic study brain exists — exam.py, learning_path.py, mastery.py, prerequisite.py, progress.py, recommendation.py, retention.py, weakness.py in the backend — mirroring the proven Mastery-platform math. But an engine without a syllabus is a library with no books: the content store has its four wings built (concepts/, knowledge-graph/, questions/, versioning/) and nothing shelved. Building the kitchen before the first recipe is either foresight or procrastination; the pipeline’s first full syllabus run will decide which.

Versioning is designed, not yet exercised. Content versions, knowledge-graph updates, gap-and-duplicate detection — all specified in docs/, none battle-tested, because there is no v1 to version yet. The design is sound on paper: every explanation carries its syllabus mapping and version, updates never overwrite. Paper is where all versioning schemes look easy.

And the empty room, stated plainly: the store is built and empty. This page documents an architecture with a pilot light on, not a platform with students. Everything below describes what exists (engine, pipeline scaffolding, runtime skeleton, docs) versus what is next (first syllabus run, validation evidence, learners).

The decisions

Zero runtime LLM dependency

Problem
Per-request model calls make answers slow, expensive, non-reproducible — and aGo down with every provider outage.
Options considered
  • Live LLM tutoring
  • Cached LLM responses
  • Offline generation, deterministic serving
Chosen
AI works only in the offline pipeline (extract, generate, validate, version, publish); the website runtime serves the content store through deterministic APIs like GET /api/concepts/{id}.
Why
Instant answers, zero per-student inference bill, identical answers for identical questions, and survival when providers go dark. Reproducibility is a feature students can feel.
Trade-offs
Content freshness lags the world by one pipeline run; interactive Socratic tutoring is impossible without runtime generation; the pipeline itself still needs model budget and supervision.
Result
The runtime has no model key to leak, no per-click cost to meter, and nothing to hallucinate at serving time.

Versioned content with syllabus mappings

Problem
Syllabi change and questions rot; students need to know what each item covers and which version they studied.
Options considered
  • Unversioned question bank
  • Versioned content + syllabus graph
  • External CMS
Chosen
Content store with concepts, knowledge graph, questions, and versioning wings; every item maps to syllabus sections.
Why
When Databricks reshuffles the exam, the mapping shows exactly which items die — updates become queries, not archaeology.
Trade-offs
Versioning machinery with no v1 yet is speculation with good posture. The knowledge-graph schema may not survive first contact with real syllabus sprawl.
Result
Structure ready; awaiting the first syllabus run to prove or reshape it.

Deterministic study engine, not recommendations-as-a-service

Problem
Adaptive paths need scheduling math, prerequisites, retention, and weakness modeling — without per-student inference.
Options considered
  • LLM-driven tutoring
  • Rules + scheduling arithmetic
  • Buy a learning platform
Chosen
Eight algorithm modules (exam, learning path, mastery, prerequisite, progress, recommendation, retention, weakness) — the Mastery-platform lineage, adapted for certifications.
Why
Same inputs, same path; every recommendation explainable; zero marginal cost per learner. Proven sibling math beats novel math.
Trade-offs
No conversational adaptation, no free-text understanding. The engine schedules brilliantly and converses not at all.
Result
The brain is done; it is waiting for its first books.

How it works

  • Python 3.11
  • FastAPI
  • Deterministic algorithms
  • Content store
  • Offline AI pipeline
  • Pytest
  • httpx

The whole system is two loops that meet at the store — drawn below. Six terms, explained once and never again:

  • Offline pipeline. Queue → processors (extract, generate) → validators → publishers → versioning → DB. LLMs work here, under supervision, where mistakes are cheap.
  • Content store. Concepts, explanations, examples, questions, knowledge graph, syllabus mappings, versions. The membrane between generation and serving.
  • Deterministic APIs. GET /api/concepts/{id}, syllabus sections, practice by section and difficulty. No model behind any of them.
  • Study engine. Eight modules scheduling what to learn next, tracking mastery and retention, modeling prerequisites and weakness.
  • Validators. Gap detection, duplicate detection, syllabus coverage — the pipeline’s immune system, run before publish, never after.
  • Versioning. Every item carries its version and mappings; updates add, never overwrite.

Three chains connect requirements to what got built:

Answers must be instant and reproducible → no runtime generation. The website’s hottest path touches a store and arithmetic, never a model. Latency and cost are properties of the architecture, not optimizations applied later.

Content must survive syllabus churn → mappings plus versions. The graph absorbs the change; regeneration is scoped; history is preserved. This is designed, awaiting its first real test.

Paths must adapt without inference → deterministic study math. Mastery, retention, prerequisites, and weakness modules schedule from stored state. The lineage to the Mastery platform is deliberate — proven math, new domain.

Why the store stays empty for now

An empty versioned store with a working pipeline beats a full unversioned bank. The first syllabus run will fill it or expose the schema — either outcome is progress, and both are recorded here when they happen.

Running it costs the machine plus the offline pipeline’s model budget per syllabus run — students cost nothing extra, ever. That shape is the business model as much as the architecture: fixed creation cost, zero marginal serving cost, reproducible answers as the selling point.

How AI was actually used here

Inverted from the usual: AI does the authoring, never the serving. What gets delegated: knowledge extraction from LLM interactions, explanations, examples, counterexamples, practice questions, gap and duplicate detection, learning paths. What doesn’t: anything a student touches — every served byte passed validators, versioning, and publishing first.

Verification is the pipeline itself: generate, validate, version, publish — in that order, always. A validator that never rejects is decoration; the first syllabus run will show whether these are guards or garnish.

One gap I’ll name plainly: validator quality is asserted, not demonstrated — with no content run yet, “validated” means “designed to validate.” The first syllabus is the exam the pipeline itself must pass.

Reflection

What worked. The inversion (offline AI, deterministic serving) held through every design review — no quiet runtime calls crept in. Borrowing the Mastery study math instead of inventing new math. Docs before content.

What didn’t. Nothing has failed yet, which is itself the risk — an untested pipeline is a hypothesis with folders. The empty store is honest but also the whole bet, unresolved.

What surprised me. How much of “AI platform” turned out to be versioning and mappings rather than models. The intelligence is easy to generate; knowing what it covers, which version a student saw, and what died in a syllabus change is the actual product.

What I’d change. Run the first syllabus now, even thin — one section end to end would test the pipeline, the store, the versioning, and the engine together. Thin and real beats comprehensive and theoretical.

What remains unsolved. Whether deterministic paths retain learners as well as adaptive tutors convert them — the core bet, measurable only with students. That experiment is scoped and waiting: first syllabus, then cohorts, then numbers.

Build your own

Reproduce it exactly (requirements, backend skeleton, empty store — the store being empty IS the checkpoint), then: run the first syllabus section through processors → validators → versioning and shelve one real concept; query it back through the deterministic API and confirm zero model involvement; change one syllabus mapping and watch versioning contain the blast radius; add one validator (duplicate detection on explanations) and feel what “immune system” means in practice.

Five things worth keeping: generate offline, serve deterministically. Version everything a syllabus can kill. Borrow proven math; invent only content. Validators must reject or they’re decoration. An empty store with a working pipeline beats a full bank with no provenance.
