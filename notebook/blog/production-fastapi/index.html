FastAPI in production: three afternoons to boring reliability

Move one write server-side, enforce layers with tests, install CI gates — each step grounded in real code from a learning-platform backend.

2026-09-05

Tutorials teach endpoints; production is everything around them. The failure mode of most FastAPI codebases isn’t architecture — it’s accumulation: client-trusted writes, untestable handlers, rot nobody measures. Three afternoons, in order, each independently shippable.

Afternoon 1 — Move one write server-side

Real code from an exam-submit endpoint (backend/app/api/v1/exams.py):

Your turn: audit one write path in your project. Who decides — client or server? Move it server-side with a history comment. Then generalize: name the source of truth per concern and defend each in review. Failure mode prevented: forged progress and support tickets you cannot adjudicate.

Lesson

Juniors write tests; staff engineers make untested code unmergeable. The coverage floor matters less than its existence — the day it goes red is the day it earns its keep.

Afternoon 2 — Make layers testable, then test them

Router → service → model, no skips; Pydantic on both doors. The reference backend runs 86 unit tests in ~4 seconds precisely because services never need HTTP and algorithms never need the database. Add response models everywhere (kills serialization bugs), rate-limit auth first (5 per 5 minutes kills the easiest attack). When layering is wrong for you: weekend prototypes should stay flat — layers scale with lifespan, and premature layering is its own smell.

Afternoon 3 — Install gates that bite

Ruff, strict mypy, pytest with an 80% coverage floor, contract tests against your own OpenAPI schema, dependency audits, Docker build smoke. Then the remainder: JWT rotation, audit logs, GDPR wipe, health checks, request IDs, structured logs, pooled connections. First principle: a gate you can bypass is documentation; a required check is architecture.

What worked, what I’d change

Worked: the BUG-017 convention (history comments on trust moves) and the coverage floor as rot prevention. I’d change: strict mypy currently blocked by a 3.11-vs-3.12 config mismatch that predates this writing — gates must run green to mean anything, and a red-ignored gate is worse than none. Principle: boring reliability is an accumulation of unglamorous choices, each permanent. Next investigation: contract-test coverage of the 16-router surface, measured, not assumed.
